# Product Scope

## 목표

판매자별 쇼핑몰과 라이브 방송 운영을 하나로 제공하는 구독 플랫폼.

## 기능 범위

### 쇼핑몰

- 판매자별 쇼핑몰
- 쇼핑몰 로고는 이미지 업로드로 정한다 (2026-10-04 대표님 지시): 쇼핑몰 설정의 로고 칸을 눌러(또는 끌어 놓아) 이미지를 올리고 미리보기·바꾸기·지우기를 한다. 올린 로고가 없을 때만 쇼핑몰 이름 첫 글자를 보여 준다. 형식·저장 방식은 다른 이미지와 같다(PNG, 대표님 결정 전까지 DB 저장)
- 이벤트 팝업·홈 배너 관리 (2026-10-04 대표님 지시): 파트너스 관리자에서 이벤트 팝업(노출 기간·대상 페이지·PC/모바일·「오늘 하루 보지 않기」·미리보기)과 쇼핑몰 홈 배너(슬라이드 순서·PC/모바일 이미지·링크·기간·미리보기)를 관리하고, 구매자 쇼핑몰 홈·페이지에 보인다. 대표자와 「쇼핑몰 설정」 권한 직원만 바꾸고 변경은 로그 추적에 남긴다. 이미지 저장은 대표님 결정 전까지 비용이 들지 않는 A(DB 저장)
- 실제 쇼핑몰처럼 운영 가능해야 한다 (2026-10-04 대표님 지시): 빠진 기능은 외부 쇼핑몰 솔루션(카페24) 관리자 기능과 비교해 추가한다. 디자인 세션이 비교 목록(2026-10-04: 쿠폰, 상품 리뷰, 교환·반품, 상품 진열, 회원 등급, 통계, 쇼핑몰 FAQ, 검색 노출(SEO), 찜·최근 본 상품, 재입고 알림, 회원 대상 발송, 엑셀 일괄 등록·내보내기)을 만들었고, 대표님이 12건 모두 추가로 확정했다(2026-10-04). 디자인부터 차례로 추가한다. 뺄 기능은 대표님이 직접 목록으로 정한다. 개발 배정 순서는 MASTER가 정한다. 화면에는 외부 플랫폼 이름을 쓰지 않는다
- 쇼핑몰 파비콘·공유 미리보기(OG 카드) (2026-10-04 대표님 지시): 파트너스 관리자 쇼핑몰 설정에서 파비콘 이미지(정사각형 PNG/ICO, 없으면 로고에서 자동 생성: 정사각형으로 가운데 맞춤·여백, PNG 변환, 32·180·512px)와 공유 미리보기 제목·설명·이미지(1200×630, 없으면 쇼핑몰 이름·로고로 기본 카드)를 정한다. 그 쇼핑몰 모든 페이지의 favicon·og:title·og:description·og:image에 쓰고, 상품 상세는 상품 이름·대표 이미지가 우선한다. 대표자와 「쇼핑몰 설정」 권한 직원만 바꾼다
- 쇼핑몰 주소 (2026-10-02 대표님 결정): 가입 즉시 플랫폼 하위 기본 주소 제공 + 판매자가 직접 산 도메인(.com, .co.kr 등) 연결. 판매자가 도메인 회사에 연결 값을 넣고 플랫폼이 소유 확인 후 보안 인증서를 자동 발급
- 상품·이미지·재고 관리
- 주문 관리
- 구매자 → 판매자 문의 (2026-10-02 대표님 지시): 상품 문의(상품 상세에서, 공개·비공개 선택)와 1:1 문의(마이페이지). 판매자가 관리자에서 답변하고, 답변이 달리면 구매자에게 알림. 해당 판매자와 마스터만 볼 수 있고 다른 판매자는 볼 수 없음
- 판매자 명의 PG 연결 (플랫폼이 대금을 수취하지 않는 구조 전제)
- 구매자 계정 (2026-10-02 대표님 확정): 회원만 주문할 수 있다(비회원 주문 없음). 회원가입 시 휴대폰 본인확인 필수 (2026-10-02 대표님 지시, 2026-10-03 PASS 앱 방식에서 문자 방식으로 변경). 판매자 가입 신청 시 대표자도 휴대폰 본인확인. 대표자 1명은 쇼핑몰 1개만 열 수 있다(대표자 CI 기준, 해지된 쇼핑몰은 제외. 2026-10-02 대표님 지시). 본인인증 결과(CI)로 같은 쇼핑몰 중복 가입을 막는다
- 로그인 (2026-10-02 대표님 결정, 2026-10-03 로그인 잠금 없음 재확인): 마스터·판매자·구매자 모두 아이디(이메일)와 비밀번호가 맞으면 바로 로그인한다. 2단계 인증, 로그인 실패 잠금, 접속 IP·네트워크 제한(지정 IP)은 두지 않는다. 로그인 실패는 감사 로그에 남긴다. 판매자 비밀번호 찾기는 대표자 휴대폰 본인확인으로 하고, 인증한 사람이 그 쇼핑몰 대표자와 같으면(CI 일치) 바로 새 비밀번호를 입력한다. 메일 링크는 쓰지 않는다. 직원 계정은 대표자가 직원 계정 관리에서 재설정한다. → 2026-10-03 대표님 지시로 보완: 파트너스 로그인은 「대표자」「직원」 탭으로 나누고, 두 탭 모두 왼쪽 끝 「아이디/비밀번호 찾기」 링크 하나로 들어와 화면 위쪽 「아이디 찾기 | 비밀번호 찾기」 전환으로 오간다(회원가입은 대표자 탭 오른쪽 끝만 — 대표님 지시 2026-10-04). 직원은 첫 로그인 뒤 직원 본인 휴대폰 본인확인을 한 번 해 그 CI(해시)를 계정에 연결한다(대표자가 등록한 이름·휴대폰 번호와 맞을 때만 연결). 직원 아이디·비밀번호 찾기는 본인확인 결과의 CI가 계정에 연결된 CI와 같을 때만 허용한다(번호가 다른 사람에게 넘어가도 이름·번호만으로 복구되지 않게). CI가 연결되지 않은 직원은 스스로 찾을 수 없고 대표자에게 문의한다. 이미 있는 직원(이름은 있고 휴대폰 번호가 없음)은 대표자가 직원 관리 수정 화면에서 휴대폰 번호를 나중에 채우거나 바꿀 수 있고(이름도 고칠 수 있음), 번호를 바꾸면 연결된 CI를 지워 직원이 다시 본인확인으로 연결해야 한다(변경은 감사 로그). CI 연결은 직원 셀프 아이디·비밀번호 찾기 전용이라, 연결 전이나 연결이 풀린 동안에도 로그인·권한은 그대로이고 셀프 찾기만 안 된다. 첫 로그인 연결 안내는 「나중에 할게요」로 넘길 수 있다(2026-10-04 MASTER). 이 조건을 만족하면 직원은 아이디(이메일)를 보거나 새 비밀번호를 정한다(맞지 않거나 번호 미등록이면 대표자에게 문의, 대표자 재설정도 그대로 가능). 한 사람이 여러 쇼핑몰에 계정이 있으면 본인확인 뒤 맞는 계정을 쇼핑몰 이름과 함께 모두 보여 주고(아이디 찾기), 비밀번호 찾기는 쇼핑몰을 하나 골라 그 계정만 재설정한다. 같은 쇼핑몰 안에서도 맞는 계정이 둘 이상이면 계정(로그인 이메일)을 함께 보여 주고 하나를 골라 그 계정만 재설정한다.
- 본인확인 횟수 제한 (2026-10-02 대표님 결정, 2026-10-03 휴대폰 본인확인으로 명칭 변경): 판매자 비밀번호 찾기의 휴대폰 본인확인 시작은 쇼핑몰 하나당 하루 10회까지다(KST 자정 초기화). 넘으면 「오늘은 더 인증할 수 없어요. 내일 다시 시도해 주세요」를 보여 주고, 초과 시도는 감사 로그에 남긴다. 아이디 찾기와 쇼핑몰을 미리 모르는 비밀번호 찾기(대표자·직원 모두, 2026-10-03 추가)는 본인확인 시작 전에 휴대폰 번호와 접속 IP로 제한한다: 같은 휴대폰 번호 하루 10회, 같은 접속 IP 하루 30회(KST 자정 초기화, 아이디 찾기·비밀번호 찾기 합산). 쇼핑몰 주소를 입력한 비밀번호 찾기는 쇼핑몰 하나당 하루 10회도 함께 적용한다. 넘으면 같은 안내를 보여 준다(2026-10-04 MASTER 보완)
- 구매자 알림 (2026-10-02 대표님 확정): 카카오 알림톡으로 보내고 실패하면 문자로 대신 보낸다. 「내 차례 알림」은 두지 않는다(대표님 결정 2026-10-02 변경)
- 구매자 메일 (2026-10-02 대표님 결정): 알림톡·문자와 함께 가입 이메일로 주문 메일을 보낸다. 종류는 주문 완료 · 발송(송장 조회 버튼) · 배송 완료 · 취소·환불 4가지. 받는 분 이름·연락처·주소는 가리지 않고 그대로 보여 준다(대표님 결정). 문구는 해요체. 판매자가 종류별로 켜고 끌 수 있다(SA-080). 메일 발송 업체·비용은 대표님 승인 대상
- 개인정보 표시 (2026-10-02 대표님 결정): 판매자·마스터 관리 화면(주문, 배송, 회원, 문의 등)과 주문 메일에서 구매자 이름·연락처·주소를 가리지 않고 그대로 보여 준다. 열람·내보내기는 감사 로그에 남긴다. 다른 구매자에게 공개되는 화면(상품 문의 작성자 등)은 방송 닉네임만 보여 준다
- 판매자 직원 계정 (2026-10-02 대표님 결정): 고정 역할(매니저·방송 담당)로 나누지 않고 권한 항목으로 나눈다. 쇼핑몰 대표자가 직원 계정을 직접 만들고, 항목별로 권한을 켜고 끈다. 항목: 방송 진행(주문대기·개봉) · 오버레이 편집 · 상품 · 주문·배송 · 고객 정보 보기(이름·연락처·주소) · 회원·적립금 · 문의 답변 · 영수증·세금계산서 · 매출 보기 · 쇼핑몰 설정. 결제(PG) 연결·구독·직원 관리·실지급 스위치는 대표자만. 자주 쓰는 묶음(예: 「방송만」)은 버튼으로 한 번에 고를 수 있다. 권한 변경은 감사 로그에 남긴다
- 판매자 가입 순서 (2026-10-02 대표님 결정, 2026-10-04 체험 부분 대체): 가입 신청(이때 「지금 운영 중인 쇼핑몰이 있나요?」로 플랜을 정한다: 있어요 → 오버레이 전용, 없어요 → 쇼핑몰 통합. MASTER 해석 2026-10-04, 체험 시작점이 승인 시각이라 플랜을 승인 전에 정해야 함) → 마스터 승인(오버레이 전용은 이때 7일 체험 시작, 통합은 체험 없음) → 승인 안내(메일·알림톡) → 판매자 로그인 → 오버레이 전용은 체험 7일 뒤 런칭 할인가로 구독 결제, 쇼핑몰 통합은 체험 없이 구독 결제 후 사용(아래 「ONQ 통합 지시」·「미확정」 ③이 정본). 로그인 아이디(이메일)와 비밀번호는 판매자가 가입 신청 때 직접 정한다(플랫폼이 초기 비밀번호를 만들어 주지 않는다). 승인 안내에는 판매자 관리자 주소와 로그인 이메일, 다음 할 일을 담는다. 첫 로그인 때 「시작하기」 체크리스트를 플랜별로 보여 준다 — 쇼핑몰 통합: 쇼핑몰 정보 → PG 연결 → 상품 등록 → 오버레이 주소 복사 / 오버레이 전용: 외부 쇼핑몰 주소 확인·연동 → 오버레이 설정 → 오버레이 주소 복사(통합 기능 단계는 보이지 않음, 2026-10-04)
- (대체됨 2026-10-04: 체험은 오버레이 전용 7일만, 아래 「미확정」 ③) 체험 (2026-10-02 대표님 결정 · 같은 날 3일 → 14일로 변경, 화면 표기는 「체험하기」 — 「무료 이용」이라고 쓰지 않는다): 마스터가 가입을 승인한 시각부터 14일(2주) 동안 무료로 쓴다(신청일 기준 아님). 14일이 지나면 구독을 결제해야 판매자 관리자 기능을 계속 쓸 수 있다(결제 전에는 구독·결제 화면과 로그아웃만 열림). 결제하면 바로 이어서 쓴다
- 결제 실패·잠금·해지 (2026-10-02 대표님 결정): 구독료 결제가 실패하면 하루 간격으로 3번 다시 시도하고, 실패한 날부터 7일 유예 뒤 잠근다(쇼핑몰·오버레이 멈춤, 결제하면 바로 풀림). 잠긴 지 30일이 지나면 자동 해지한다. 해지 뒤 90일 동안 데이터를 보관하고 그 뒤 삭제한다. 보관 기간 안에 다시 구독하면 데이터를 그대로 되살린다. 주문·결제 기록은 법정 보존 기간(5년) 동안 따로 보관한다. 해지·삭제 전에 판매자에게 메일·알림톡으로 미리 알린다

- 가격 변경 적용 (2026-10-02 대표님 결정): 가격을 바꾸면 새로 가입하는 판매자에게는 바로 적용하고, 기존 구독자에게는 30일 전에 메일·알림톡과 판매자 관리자 공지로 알린 뒤 그다음 결제부터 적용한다. 가격 변경은 대표님(최고관리자)만 한다

  - 탈퇴하면 회원 정보(로그인 아이디·비밀번호·연락처 등 계정 정보)는 바로 파기하거나 알아볼 수 없게 한다. 법으로 보관해야 하는 기록만 그 종류별 기간 동안 따로 분리해 보관하고 기간이 끝나면 파기한다: 계약·청약철회 기록 5년, 대금 결제·재화 공급 기록 5년, 소비자 불만·분쟁 처리 기록 3년, 표시·광고 기록 6개월, 접속 기록 3개월. 거래가 없는 회원은 거래 기록이 남지 않는다(위 접속 기록 3개월만 보관). 구매자가 한 일의 감사 로그 IP·브라우저 정보는 접속 기록 보관 기간(3개월)이 지나면 지운다. 판매자 직원·플랫폼 관리자가 개인정보를 다룬 접속 기록(감사 로그)은 이 3개월 삭제 대상이 아니며, 개인정보의 안전성 확보조치 기준 제8조에 따라 최소 1년(법이 정한 경우 2년) 보관한다(FEATURE_GAP). 탈퇴 회원의 감사 로그는 종류별로 나눈다. 주문·결제·취소·환불·배송처럼 계약·청약철회·대금 결제·재화 공급 기록에 해당하는 감사 로그만 거래 기록의 일부로 5년 보관하고, 로그인·로그인 실패·가입·회원 정보 수정 같은 거래와 무관한 감사 로그는 접속 기록 보관 기간(3개월)이 지나면 회원 id를 비식별 값으로 바꾼다. 거래 관련 감사 로그도 5년이 지나면 회원 id(행위자 id·대상 id 등 모든 칸)를 비식별 값으로 바꾼다. 법정 보관 기록(주문·받는 사람 스냅숏·결제·환불 기록과 거래 관련 감사 로그)은 탈퇴 때 「분리 보관」 표시와 보관 만료일을 달아 일반 기록과 나눈다. 분리 보관된 기록은 판매자의 주문 목록·검색·내보내기와 구매자 화면 같은 일반 조회 경로에서 빠지고, 분쟁·법령에 따른 요청 대응용 별도 조회 경로로만 볼 수 있다(권한은 최고관리자와 지정된 담당자만, 조회할 때마다 감사 로그를 남김)(개인정보 보호법 제21조 제3항). 파기 대상에는 회원 행의 생년월일과, 그 회원의 본인확인 기록이 들어간다. 본인확인 기록은 개인 식별 항목(이름·휴대폰·인증 요청 휴대폰 번호·생년월일·CI 해시·회원 연결(subjectId)·대행사 요청 번호(requestId))을 모두 비운다(요청 번호는 대행사에서 본인확인 결과를 다시 조회하는 열쇠이므로 무작위 값으로 바꾼다). 다만 행은 지우지 않고 IP별 일일 한도·체험 한도 계산에 필요한 최소 값(쇼핑몰, 상태, 요청 시각, 요청 IP)만 남겨, 가입·탈퇴를 되풀이해 한도를 다시 채우는 남용을 막는다. 요청 IP는 접속 기록과 같이 3개월 뒤 비운다(Codex 지적). 재가입 제한 정보 보관(선택)에 동의한 회원의 재가입 제한용 CI 해시만 아래 예외로 본인확인 기록이 아닌 재가입 제한 보관 자리에 따로 남긴다. 방송 닉네임은 회원 행뿐 아니라 주문·주문대기·HIT 카드에 복사된 닉네임까지 탈퇴 때 「탈퇴한 회원」으로 바꾼다(닉네임은 법정 보관 기록이 아님). 로그인 세션 기록은 폐기 표시만 하지 않고 탈퇴 때 삭제한다. 탈퇴하지 않은 회원의 끝난 주문은 회원 서비스(주문 내역 조회, 교환·반품·고객 문의 응대)의 이용 목적으로 계속 보관한다(처리방침 2-(1)-③: 탈퇴 시 또는 주문이 끝난 날부터 5년 중 먼저 오는 때까지). 그래서 분리 보관 표시는 탈퇴 때 단다. 다만 보관 기간은 탈퇴하지 않은 회원의 거래 기록에도 같이 적용한다: 각 기록의 기준일(주문은 구매 확정·취소·환불이 끝난 날, 감사 로그는 남긴 날)부터 기간을 세고, 기간이 지나면 받는 사람 스냅숏 같은 개인정보를 파기하거나 알아볼 수 없게 하고 감사 로그의 회원 id를 비식별 값으로 바꾼다(정기 실행, Codex 지적). 거래와 무관한 감사 로그(로그인·로그인 실패·가입·회원 정보 수정)의 3개월 비식별도 탈퇴 여부와 상관없이 모든 회원에게 적용한다. 원칙: 회원 id를 가진 모든 표는 「탈퇴 때 삭제」·「비식별」·「법정 보관(기간 뒤 파기)」 중 하나로 분류하고, 새 표가 생기면 분류를 빠뜨리지 않도록 표 목록 검사 테스트를 둔다
  - 재가입 제한은 판매자 설정으로 둔다(기본 사용 안 함). 쓰면 판매자가 정한 기간 동안 같은 사람(본인확인 기준)이 다시 가입할 수 없다. 회원마다 가입 때 동의한 제한 기간을 기록하고, 탈퇴 때는 그 기간과 지금 설정 중 짧은 쪽만 적용한다(동의하지 않은 더 긴 기간으로 보관하지 않음). 재가입 제한을 켜기 전에 가입한 회원(별도 동의와 기간 기록이 없는 회원)에게는 적용하지 않는다. 다시 동의를 받는 기능은 만들지 않는다. 이를 위해 재가입 제한이 켜진 쇼핑몰에서만 탈퇴 회원의 본인확인 식별값 해시(ciHash) 하나를 「재가입 제한」 목적으로 제한 기간 동안 남기고, 기간이 끝나면 파기한다. 이름·휴대폰 등 다른 정보는 남기지 않는다. 개인정보처리방침의 보유 기간에 이 항목을 적는다. 가입 화면에서는 이 보관을 「개인정보 수집·이용」과 다른 별도 **선택** 동의 항목으로 받는다(재가입 제한이 켜진 쇼핑몰만, 기본 체크 안 함, 동의 기록도 따로 저장). 동의하지 않아도 가입할 수 있고, 동의하지 않은 회원은 탈퇴 뒤 재가입 제한을 받지 않으며 CI 해시도 남기지 않는다(2026-10-03 대표님 결정, 개인정보 보호법 제22조 제5항). 동의한 회원은 회원 정보 화면에서 언제든 철회할 수 있고, 철회하면 동의 기간 기록을 지우고 철회 시각을 남기며, 탈퇴 때는 가입 때 기록이 아니라 지금 동의 상태를 보고 보관·제한 여부를 정한다(개인정보 보호법 제37조). 근거는 이용약관 제6조의 재가입 제한 조항이다

- 상품명 길이 (2026-10-03 대표님 결정, 네이버 스마트스토어·쿠팡 기준 참고): 상품명은 공백 포함 최대 100자. 넘으면 저장하지 않고 안내한다. 입력 칸에 글자 수(예: 42/100)를 보여 주고, 목록에서 잘 보이도록 50자 이내를 권장한다
- 상품 이벤트 할인·마감 임박 표시 (2026-10-03 대표님 결정, 쿠팡·네이버 쇼핑 방식 참고): 판매자가 상품마다 이벤트 할인(할인율 또는 할인 금액)과 시작·종료 시각을 정한다. 기간 동안 정가 취소선 + 할인율 + 할인가를 보여 주고, 끝나면 자동으로 정가로 돌아간다. 종료가 가까우면 「오늘 마감」·「D-3」 배지와 「3시간 12분 남았어요」 같은 남은 시간(타임딜 카운트다운)을 상품 목록·상세·방송 오버레이에 보여 준다. 할인 적용 여부와 금액은 주문할 때 서버가 DB 시계로 판단하고, 주문에 그때 금액을 남긴다(기간이 끝나도 이미 만든 주문 금액은 바뀌지 않음)
  - 할인은 단가(상품 가격 + 옵션 추가금)에 적용하고 할인가는 원 단위 버림이다. 할인율은 1~90%, 할인 금액도 가격의 90%까지. 시각은 오프셋이 붙은 ISO 8601로만 받는다 (2026-10-03 MASTER 검수)

### 적립금 (판매자별)

- 신규 개발. 망고TCG 적립금 기능은 참고만 하고 코드는 이식하지 않음
- 판매자별 적립금 정책: 회원 등급별 적립률(카드/무통장 구분), 지급 시작 시점
- 적립금 지급 시점 (2026-10-03 대표님 결정): 판매자가 「결제 즉시 지급」과 「배송 완료 후 지급」 중에서 고른다(기본 배송 완료 후 지급). 결제 즉시 지급한 뒤 취소·환불되면 지급한 적립금을 회수한다(원장에 회수로 남김)
  - 적립은 결제 시점 스냅숏으로 판정한다(2026-10-03 MASTER 결정): 지급 시점·회원 등급·적립률·적립 예정액을 결제 때 주문에 남기고 지급 시작일도 결제 시각 기준. 배송 완료 후 지급이면 그 예정액을 배송 완료 때 지급 대기로 기록한다. 결제 때 0원이면 나중에도 적립하지 않는다
- 주문 결제 완료 시 지급, 취소·환불 시 회수 (자동/수동 회수 모드)
- 적립 기준 금액 (2026-10-03 대표님 결정): 할인 후 상품 금액에 적립률을 곱한다. 배송비는 빼고, 적립금으로 결제한 금액은 빼지 않는다(예: 할인 후 상품 금액 310,200원 × 3% = 9,306원)
- 판매자별 적립금 원장(지급·회수·실패 이력)과 회원별 잔액
- 구매 랭킹 보너스: 명예의 전당 1위 적립금 보너스는 판매자가 켜고 금액을 정한다 (기본 꺼짐, 2026-10-02 대표님 확정)
- 실지급은 판매자별 실행 스위치(기본 꺼짐)로 통제. 개발·검증 단계에서는 테스트 모드만 사용

### 세금계산서·현금영수증 (2026-10-02 대표님 지시)

- 구매자 → 판매자 쇼핑몰: 무통장·계좌이체 결제 시 주문서에서 현금영수증 신청(소득공제용 휴대폰 번호 / 지출증빙용 사업자등록번호). 사업자 구매자는 세금계산서 신청(사업자 정보 입력). 카드 결제는 카드 매출전표로 대신해 별도 발행하지 않는다
- 발행 주체는 판매자(판매자 명의). 판매자 관리자에서 신청 목록·발행 상태(대기 · 발행 · 실패 · 취소)를 보고, 환불 시 발행 취소(마이너스 발행)를 함께 처리
- 플랫폼 → 판매자 (2026-10-02 대표님 결정): 구독료는 카드 자동결제(정기결제)로만 받는다(계좌이체·무통장 없음). 카드 매출전표가 세금계산서를 대신하므로 구독료 세금계산서는 발행하지 않는다(이중 발행 금지). 판매자는 SA-090에서 카드 매출전표를 내려받는다. 판매자 매출(판매자 → 구매자)의 영수증·세금계산서는 판매자 명의로 판매자가 발행하고, 플랫폼은 발행 기능만 제공한다. 세무 처리는 오픈 전 세무사 확인 권고
- 발행 연동 방식 (2026-10-03 대표님 결정): 발행 대행 서비스 API로 하고 업체는 바로빌이다(키 `BAROBILL_API_KEY`). 요금·계약 조건은 연동 전에 확인한다(유료, 대표님 승인)

### 배송·정책 결정 (2026-10-02 대표님 확정, 근거 `docs/FEATURE_GAP.md`)

- 배송: 구매자가 주문할 때 「즉시 발송」 또는 「보관 후 합배송」을 고른다. MVP는 즉시 발송(배송지·배송비·도서산간·송장 입력·발송 알림), 보관·합배송(보관 기한 포함)은 출시 후 1차
- 구매자 가입·배송지 (2026-10-03 대표님 결정): 회원가입은 로그인에 꼭 필요한 기본 정보와 필수 약관 동의만 받는다. 배송지는 가입 때 받지 않고 첫 주문 때 입력받는다. 주문 때 입력한 배송지는 자동으로 저장되고(구매자가 끌 수 있음), 여러 개를 저장해 두고 주문서에서 고른다. 기본 배송지 1개를 지정할 수 있고, 마이페이지에서 추가·수정·삭제한다
  - 우편번호·주소 입력 (2026-10-03 대표님 지시): 카카오(다음) 우편번호 서비스로 검색해 우편번호·도로명 주소를 채운다(무료·키 없음). 구매자는 상세 주소만 직접 쓴다. 서버는 받은 값을 지금처럼 다시 검사하고 도서산간도 서버가 판정한다(화면 값만 믿지 않음). 검색창을 못 띄우면 직접 입력으로 대신한다. 판매자 출고지·반품지 주소도 같은 방식
    - 적용 기준(카카오 우편번호 서비스 가이드 https://postcode.map.kakao.com/guide): 스크립트 `https://t1.daumcdn.net/mapjsapi/bundle/postcode/prod/postcode.v2.js`를 주소 검색을 열 때만 불러온다. 키 발급 없음. 팝업 차단을 피하려고 PC는 레이어, 모바일은 전체 화면에 embed로 띄운다. 결과의 `zonecode`(5자리)를 우편번호로, `roadAddress`를 기본 주소로 쓴다(구매자가 지번을 고르면 `jibunAddress`). 공동주택이면 `buildingName`을 괄호로 덧붙인다. 다 고르면 상세 주소 칸으로 포커스를 옮긴다. 가이드 원문은 MASTER 환경에서 접속이 막혀 공개 자료로 확인했고, 구현 때 화면 세션이 원문과 다시 맞춘다
- 구매자 화면은 반응형 웹만 만든다. 별도 앱은 만들지 않는다 (2026-10-03 대표님 결정). 알림은 알림톡·문자·메일로 보낸다
- 미성년자 구매: 판매자가 「미성년자 구매 막기」 / 「고지 후 허용」 중 선택(기본 고지 후 허용). 휴대폰 본인확인 생년월일로 판별, 주문서에 미성년자 취소권 고지
- 방송 시작 알림: 광고성 정보로 보고 마케팅 수신 동의 회원에게만 보낸다. 문구에 (광고) 표기와 수신 거부 방법 포함
- 알림톡·문자·가상계좌 등 건당 비용: 전부 판매자 부담(충전식). 요금제에 포함하지 않는다

### 플랫폼 마스터 관리자

- **플랫폼 마스터 관리자가 최상위 권한이다. 권한 계층: 마스터 관리자 > 판매자 > 구매자·시청자. 마스터 관리자은 모든 판매자·쇼핑몰·구독·설정을 다루며, 판매자 권한으로 마스터 관리자 기능에 접근할 수 없다. 마스터 관리자 안에서도 역할별 권한을 나눈다: 무제한 조회·변경은 최고관리자(대표님)만, 운영·CS는 담당 기능만, 조회 전용은 변경 불가.** (2026-10-02 대표님 지시)
- 마스터 관리자 운영 (2026-10-02 대표님 결정): 마스터 관리자은 대표님 혼자 운영한다. 운영·CS·조회 전용 역할 계정은 지금 만들지 않는다(역할 구조는 코드에 남겨 둔다). 대리 조회 때 구매자 이름·연락처·주소는 그대로 보인다(열람은 감사 로그). 마스터의 반복 업무는 사람이 처리하지 않도록 자동화한다
- 휴대폰 본인확인 방식 (2026-10-03 대표님 결정): PASS 앱 설치·실행·앱 전환을 요구하지 않고, 본인확인기관 대행사의 정식 「문자로 본인확인」(명의 정보 대조 + 문자 인증번호 입력)으로 한다. 일반 문자 발송 API로 번호 소유만 확인하는 방식은 쓰지 않는다. 화면 명칭은 「휴대폰 본인확인」, 방식 설명은 「문자로 본인확인」
- 테스트 환경 본인확인·결제 우회 (2026-10-03 대표님 결정): 테스트 서버(obs-test)에서는 휴대폰 본인확인을 실제 대행사 없이 통과시킨다. 서버 환경변수로만 켜고(운영 서버에는 두지 않는다), 켜져 있으면 화면과 `/api/health`에 테스트 모드임을 표시한다. 결제도 같은 테스트 모드에서 우회한다(같은 날 대표님 결정): 판매자 구독 결제와 구매자 주문 결제 모두 실제 PG 호출 없이 성공 처리하고, 실제 돈은 오가지 않는다. 구매자 주문 결제 우회는 구매자 PG 결제를 도입할 때 함께 적용한다. 그 전에는 구매자 주문이 무통장 입금뿐이라(우회할 PG 호출 없음) 테스트 서버에서도 판매자 입금 확인으로 결제 완료 이후 흐름을 시험한다(2026-10-04 MASTER 결정). 운영 서버의 본인확인·가입·결제 규칙은 그대로다. 구현은 PR #157(테스트 서버 모드 `OBS_TEST_MODE=1`, 가드 예외·`/api/health` testMode·DEPLOY.md 갱신)에서 하며, 병합·서버 반영 전까지 obs-test는 기존대로 본인확인 503·구독 결제 실패 상태다(변경 예정).
  - 화면: 대행사가 허용하면 자체 화면(인적사항 입력 → 약관 동의 → 인증번호 받기 → 인증 확인), 허용하지 않으면 대행사 공식 인증창(PC 팝업·모바일 페이지 전환). 주민등록번호 전체는 받지 않는다. 자릿수·유효시간·재전송 규칙은 대행사 규격을 따른다
  - 문자 단독(PASS 선택지 없음) 제공이 계약·기술상 가능한지 대행사 확인 전까지는 차단 조건이다. 확인 전에는 「PASS 없이 문자만」이라고 안내하지 않는다
  - 후보 구성 (2026-10-03 MASTER 조사, 포트원 공개 문서 기준): 포트원 V2 + NHN KCP 채널 「API 방식」. 서버가 인증번호 요청(`method: SMS`) → 사용자가 자체 화면에 인증번호 입력 → 서버가 확인 → 서버 단건 조회로 `VERIFIED` 확정. 같은 요청 id는 한 번만 성공한다. 입력은 이름·휴대폰번호·생년월일과 성별 자리(주민번호 앞 7자리)·통신사(알뜰폰 포함). KCP 표준창은 인증 수단을 문자로 제한하는 설정이 문서에 없다. KCP 원문 가이드·NICE·KCB·SCI 문서는 접속이 막혀 확인하지 못했다
  - 결과는 서버 간 조회·복호화로만 확정한다(브라우저 성공 표시·콜백 값만으로 완료하지 않음). 요청은 현재 가입 세션에 묶고, 다른 사용자 결과 재사용·같은 결과 반복 사용·만료 결과를 막는다. 완료 뒤 휴대폰번호 등 인증 대상 정보가 바뀌면 다시 인증한다
  - 인증 이력에는 대행사·방식·완료 시각을 남긴다. 과거 이력의 방식은 바꾸지 않는다. 사용량은 인증 성공 1건을 한 번만 세고, 대행사 과금 건수와 따로 본다
  - 운영에서 계약·키·필수 설정이 없으면 「본인확인 서비스 준비 중」으로 안내하고 가입을 막는다. 가짜 인증은 개발·테스트에서만 쓴다
  - 휴대폰 본인확인은 사업자 확인·판매자 승인·PG 승인과 별개다. 본인확인 성공만으로 승인·정산 가능 상태를 만들지 않는다
- 판매자 가입 자동 승인 (2026-10-02 대표님 결정): 가입 신청이 들어오면 자동 점검(대표자 휴대폰 본인확인, 대표자 CI 중복 = 쇼핑몰 1개 규칙, 국세청 사업자 상태 「계속사업자」와 진위확인(대표자명·개업일 대조), 같은 사업자번호로 운영·신청 중인 쇼핑몰 없음, 통신판매업 신고 조회(공정위))을 돌린다. 모두 통과하면 자동 승인하고 승인 안내를 보낸다. 하나라도 걸리면 승인하지 않고 마스터 관리자 「확인 필요」에 올려 대표님이 직접 승인·보완 요청·반려한다. 자동 승인도 감사 로그에 남긴다
- 대표·플랫폼 운영팀 전용 통합 관리 콘솔 (판매자 관리자와 분리)
- 판매자 가입 승인·정지, 판매자별 쇼핑몰·구독·PG 연결·방송 현황 조회
- 요금제·구독·구독료 청구 관리, 결제 실패·연체 관리
- 고객지원(문의·공지), 관리자 계정·역할별 권한, 감사 로그
- 판매자 화면 대리 조회는 읽기 전용, 접근 기록 필수
- 파비콘·공유 카드 설정 (2026-10-04 대표님 지시): 마스터 관리자에서 마스터 관리자와 파트너스 관리자의 파비콘·OG 카드를 각각 설정한다. 파비콘은 PNG·ICO만 받는다. OG 카드는 이미지(1200×630)를 직접 올리거나 제목으로 만든다. 변경은 최고관리자만 할 수 있고, 변경 내역은 감사 로그에 남긴다. 이미지 저장 방식(A DB 저장 / B 유료 버킷)은 대표님 결정 전까지 비용이 들지 않는 A로 한다

### ONQ 통합 지시 (2026-10-04 대표님 결정, 원문 요약. 구현 계획·검증 표: `docs/ONQ_PLAN.md`)

- 브랜드 ONQ / OnAirCue, 도메인 `on-aircue.com`. 가격은 아래 「가격」.
- 판매자 온보딩 첫 질문 「지금 운영 중인 쇼핑몰이 있나요?」
  - 있어요: 운영 중인 쇼핑몰 주소 입력 → 서버가 연결 가능 여부 자동 확인(플랫폼 이름 비노출, 플랫폼을 고르지 않음) → 연동 인증·웹훅 연결 → 오버레이 설정. 오버레이 전용 구독으로 쓸 수 있다.
  - 없어요: 쇼핑몰 통합 안내·구독 → ONQ 스토어 개설 → 상품·주문 설정 → 오버레이 설정.
  - 기존 쇼핑몰이 있는 것과 사업자인 것은 별개다. 기존 쇼핑몰이 있어도 통합 이용·전환을 막지 않는다.
  - 오버레이 전용은 서비스에 필요한 최소 계정 정보만 받는다. 사업자등록번호·상호·대표자명·사업장 주소·통신판매업 정보·정산 계좌를 필수로 하거나 없다고 이용을 막지 않는다. 이 정보는 통합으로 전환해 실제 판매·결제·정산을 켤 때 받는다(위 「판매자 가입 자동 승인」의 사업자 점검은 그 단계에 적용한다).
  - 중간에 나갔다 다시 이어 하기, 외부 쇼핑몰 추가, 플랜 전환, 기존 계정 호환을 지원한다.
- 자동 설치·연결 상품 (일회성 110,000원)
  - 사람이 원격으로 대신 설치하는 서비스가 아니라 Gemini 기반 자동 설치·연결이다. 직접 설정은 무료이고, 자동 연결은 선택형이다(기본 추가·자동 결제 없음, 월 구독료와 별도 결제).
  - 흐름: 판매자 화면 배너 → 안내 페이지(작업 범위·가격·고객이 준비할 인증·권한·PC 연결) → 결제 → 자동 연결 → 실제 작동 검증 → 완료. 배너는 상태에 맞게(시작 / 이어서 연결 / 진행 확인 / 완료 설정 확인).
  - 범위: 외부 쇼핑몰·웹훅 연결, OBS 오버레이 설치, 주문 표시·디자인 설정, 테스트 이벤트 검증.
  - 서버가 결제를 검증한 뒤에만 실행 권한을 준다(성공 리다이렉트만으로 실행 금지). 결제 상태와 연결 작업 상태를 따로 두고 중단 후 이어 하기·재시도·취소를 처리한다. 연결 작업을 시작하기 전(대기 중·결제 직후)에 고객이 취소하면 작업을 하나도 실행하지 않고 전액 환불(카드 승인 취소)한다(MASTER 해석, 2026-10-04).
  - 공식 API·OAuth·앱 설치를 먼저 쓰고, API로 안 되는 관리 화면에만 Gemini 브라우저 제어를 쓴다. Gemini 판단과 실제 브라우저 실행기는 따로 만들고 따로 검증한다. 고객 PC의 OBS는 로컬 연결 도구 + OBS WebSocket으로 연결한다(서버 브라우저가 고객 OBS를 직접 제어한다고 가정하지 않는다).
  - 로그인·2단계 인증·CAPTCHA·권한 승인·로컬 도구 설치는 고객이 할 일로 보여 주고, 끝나면 자동으로 이어 간다. 완전 무인을 약속하지 않는다.
  - 고객별 브라우저 context·쿠키·자격증명·임시파일·OBS 연결을 격리하고, 비밀값은 모델 입력·로그에서 뺀다. 구매자 이름·전화·주소·주문 내용 등 개인정보도 화면 캡처·페이지 내용을 모델(Gemini)에 보내기 전에 가리거나 빼고, 모델 제공자는 입력을 학습에 쓰지 않고 보관하지 않는 설정(유료 API 조건)으로 쓴다. 고객 대기로 보관하는 쿠키·저장소·자격증명과 임시 파일(화면 캡처·내려받은 파일·실행 기록)·OBS 연결 정보는 암호화해 그 작업에만 묶고, 완료·취소·실패·고객 행동 마감(24시간) 때 바로 지운다(단 바꾼 설정을 되돌리지 못해 「정리 필요」인 동안은 되돌리기 재시도에만 쓰는 암호화된 정리 전용 사본만 남기고, 되돌리기 완료나 자격증명 만료가 확인되면 지운다). 지운 뒤에는 다시 쓸 수 없다. 고객 행동 마감(24시간)이 지나면 작업은 실패로 끝나고 확정 ②대로 결제 금액(110,000원 또는 33,000원)을 전액 환불한다. 고객 대기를 포함한 전체 기간은 시작부터 72시간을 넘지 않는다(넘으면 실패·전액 환불, 보관 자료는 아래 되돌리기 뒤 삭제). 실패로 끝날 때는 작업이 만든 변경(쇼핑몰 연동 앱·웹훅, OBS에 추가한 소스·설정)을 되돌린 뒤 끝내고, 되돌리기가 안 되면 「정리 필요」로 두고 마스터 관리자에게 알린다. 결제 확인 뒤 24시간 안에 실행을 시작하지 못하면(작업자 부족·장애) 외부 행동 없이 실패로 끝내고 전액 환불한다. 고객 대기를 뺀 실제 실행 시간이 합계 6시간을 넘으면(브라우저·판단 모델·외부 API 멈춤, 재시도 포함) 실패로 끝내고 같은 방식으로 전액 환불한다. 연결 작업을 시작한 뒤 고객이 취소하면 그 즉시 이후 외부 행동을 멈추고(실행 중 작업자는 fencing으로 차단) 보관 자료를 지우며, 결제는 단순 변심이라 환불하지 않는다(MASTER 해석, 2026-10-04). Cafe24부터 실제 검증하고 다른 플랫폼은 하나씩 검증 후 지원 목록에 올린다. 실제 테스트 표시를 확인하기 전에는 완료로 두지 않는다.
  - 위 「판매자 도우미」(답변만)와는 별개 상품이다. 도우미 범위는 그대로다.
- 동시 실행·급성장 대응: 쇼핑몰·주문 처리와 자동 설치 작업을 분리한다. idempotency(판매자·결제·작업별), 같은 OBS 대상 잠금, worker lease·fencing, 작업 큐·동시성 제한·판매자별 공정 처리·rate limit·backoff/jitter·timeout·비용 상한·대기 표시. 인증 대기 작업이 실행 자리를 붙잡지 않는다. 주문·이벤트는 내구성 있게 보존하고 중복·누락·역순을 대사한다. 0% 오류 대신 측정 가능한 용량·가용성·탐지·복구 목표를 세우고 실측 근거를 남긴다. VM 한 대를 고가용성 완료로 표현하지 않는다.
- 마스터 관리자 자동 운영·실시간 감시: 대표님 판단이 필요한 것 외에는 자동화한다(자동 처리와 수동 판단 경계를 기능별로 적는다). 판매자·플랜·할인·온보딩·외부 연동·쇼핑몰·주문·결제·재고·배송·오버레이·자동 설치 작업·비용·실패·감사 기록을 실제 데이터로 조회하고, 목록·합계가 원장과 맞아야 한다. 화면을 닫아도 서버 감시는 계속되고, 화면은 재연결·누락 보정·마지막 갱신 시각·감시 끊김을 보여 준다. 오류 → 장애(incident) 묶기 → 영향·심각도 → 미리 허용한 안전한 자동 조치 → 복구 검증 → 감사 기록·알림. 무한 재시도·재시작 반복·알림 폭주를 막는다. 실결제·환불·운영 DB 삭제·유료 확장·롤백 정책은 이 자동화로 승인하지 않는다.
- 배송·송장: 오버레이 전용은 외부 쇼핑몰에서 배송을 관리하고, 통합은 ONQ에서 송장을 한꺼번에 출력하는 방향(제안). 굿스플로 등은 후보일 뿐 업체·API 계약·요금·택배사·프린터 환경은 미확정이다. 흐름: 주문 선택 → 합배송·주소 확인 → 배송 접수·송장 발급 → 출력 → 주문에 송장 반영 → 추적. 발급·출력·집하·배송 완료는 서로 다른 상태다(출력만으로 배송 완료 금지). 판매자별 계약·출고지·프린터 격리, 재출력과 재발급 구분, 부분 실패·취소 주문 차단.
- 외부 쇼핑몰 플랫폼 이름(Cafe24 등)은 화면·API 화면용 문구·메일·알림 어디에도 보이지 않는다(2026-10-04 대표님 결정, 예외 없음, 로고·아이콘 포함). 판매자는 플랫폼을 고르지 않고 운영 중인 쇼핑몰 주소를 넣으며, 서버가 연결 가능 여부를 판별해 「연결할 수 있는 쇼핑몰이에요 / 아직 연결할 수 없는 쇼핑몰이에요」로만 안내한다. 내부 코드 식별자는 그대로 쓸 수 있다.
- 출시 차단: 권한 우회, 판매자 데이터 섞임, 중복 결제·설치, 주문 손실, 재고·환불 불일치, 허위 자동화 완료.
