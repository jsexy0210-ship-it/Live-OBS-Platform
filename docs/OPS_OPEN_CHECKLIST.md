## 2. 운영 서버 `.env` 필수 이름(값은 서버에서만)

배포 전 검사가 요구하는 이름: `POSTGRES_USER` · `POSTGRES_PASSWORD` · `POSTGRES_DB` · `IDENTITY_HASH_KEY` · `BILLING_KEY_SECRET` · `OBS_SITE_ADDRESS` · `OBS_ENVIRONMENT=prod`. `OBS_TEST_MODE`는 넣지 않습니다.

**대표님 확인 항목:** 운영 서버 `.env`의 `OBS_SITE_ADDRESS`가 실제 운영 호스트 이름(예: 지정 주소)으로 들어 있는지 서버에서 확인해 주십시오. 비어 있거나 `:80`이면 HTTPS가 열리지 않고, 파트너스 초대 링크도 주소 없이 경로만 나옵니다(마스터 관리자 화면이 보고 있는 주소를 붙임). 값은 문서·대화에 적지 않고 서버에서만 확인합니다.

기능이 켜지려면 추가로 필요한 이름(코드가 읽는 것, 없으면 해당 기능이 막힘): `PORTONE_API_SECRET` · `PORTONE_STORE_ID` · `PORTONE_IDENTITY_CHANNEL_KEY`(휴대폰 본인확인), `NICEPAY_CLIENT_KEY` · `NICEPAY_SECRET_KEY`(주문 카드 결제), `BILLING_PROVIDER`(구독 결제), `NTS_BUSINESS_STATUS_API_KEY` · `FTC_MAIL_ORDER_API_KEY`(가입 사업자·통신판매업 점검), `TRUSTED_PROXY_HOPS`(프록시 뒤 IP 판단), `IMAGE_STORAGE`와 `BACKUP_S3_*`(이미지·백업 저장소). 나머지 선택 이름은 `docs/DEPLOY.md` 「서버 `.env`」 표를 따릅니다.

## 3. 외부 업체 미연동 때의 동작(코드 기준) — 오픈 차단 후보

| 기능 | 키·계약이 없을 때 | 운영에서 실제로 쓰려면 |
| --- | --- | --- |
| 휴대폰 본인확인 | 운영 빌드는 포트원 설정이 다 있을 때만 동작. 없으면 503 「본인확인 서비스 준비 중이에요」로 막고 500으로 터지지 않음(`lib/server/identity/registry.ts`) | 대행사 계약·키(어댑터는 포트원으로 구현돼 있음) |
| 주문 카드 결제 | 키가 없으면 「결제 준비 중」으로 거절, 돈이 움직이는 경로를 열지 않음. **키가 있어도 코드는 나이스페이 샌드박스 주소(`NICEPAY_SANDBOX_API`)만 부름** | 운영 계약 뒤 **운영 주소를 부르는 코드 변경이 먼저 필요**(키만 넣어서는 운영 결제가 나가지 않음) |
| 구독 카드 자동결제 | `BILLING_PROVIDER`가 `fake`가 아니면 결제 공급자를 만들 때 오류가 나고, `fake`여도 운영 빌드(`NODE_ENV=production`)는 가짜 공급자 생성 자체를 거부함(`lib/server/billing/registry.ts`, `provider.ts`). **실제 업체 어댑터는 아직 없고 fake만 있음** → 운영에서는 구독 결제 경로가 오류로 멈춤(실제 결제가 성공한 것으로 처리되지는 않음) | 업체 선정·계약과 어댑터 구현이 먼저 필요 |
| 가입 사업자·통신판매업 점검 | 실제 조회 어댑터가 없어 `fake`가 아니면 조회 실패로 처리 → 신청 사유에 `business_lookup_failed`·`mail_order_lookup_failed`가 남음(`lib/server/sellers/businessCheck.ts`, `application.ts`). 자동 승인 대신 점검 실패 흐름을 탐 | 공공 API 키·어댑터 구현. 오픈 당일 가입 처리 방식은 별도 결정 |

위 네 줄이 해결되지 않으면 「가입 → 구독 결제 → 주문 결제」의 운영 여정 중 일부가 막히거나 샌드박스로만 동작합니다. **코드 변경이 필요한 항목은 오픈 일정에 직접 영향**을 줍니다(구독 결제 어댑터, 나이스페이 운영 주소).

## 4. 사람만 할 수 있는 조치(대표님·MASTER 확인 필요)

1. GitHub 저장소 Environment `production` 생성, Required reviewers에 대표님, 배포 브랜치 `main`만(러너 등록보다 먼저). 현재 설정은 미확인.
2. 운영 VM·데이터 디스크·공인 IP·보안그룹 생성(80·443 전체, 22는 허용 IP만). 카카오클라우드 자원 생성은 승인 범위 확인 필요. 현재 존재 여부 미확인.
3. 운영 도메인 `on-aircue.com` A 레코드를 **운영 공인 IP**로 연결(테스트 IP를 운영에 복제하지 않음). HTTPS는 Caddy 자동 발급(80·443 필요).
4. 서버 `/opt/obs/.env` 직접 작성(권한 600, 테스트와 다른 새 값). 비밀값은 저장소·채팅에 두지 않음.
5. 러너 `obs-prod` 등록(1~4가 끝난 뒤).
6. 운영 백업 전용 버킷·전용 사용자·S3 키 발급, 수명 주기 30일, 서버에서 `db-offsite.sh` 한 번 직접 실행, cron 등록.
7. 계약·키: 결제대행사(주문 카드 결제, 구독 자동결제), 본인인증 대행사(포트원 채널), 국세청·공정위 조회 API 키.
8. 첫 운영 배포는 `deploy-obs-prod` 실행(확인 문구 `DEPLOY-PROD`, 40자 SHA)과 승인을 대표님이 직접.

## 7. 단계별 오픈 범위(대표님 「권고안대로 일괄 승인」 2026-10-26)

코드 기준 구분입니다(해당 경로가 결제·본인확인 공급자를 부르는지 확인). 운영 빌드 실측은 하지 못했습니다.

**확정 결정**
- 구매자 본인확인은 「필수 유지」(PRODUCT_SCOPE 기준)이고 끄기를 허용하지 않습니다. 구매자 가입·주문은 포트원 본인확인 계약과 키가 준비된 뒤 엽니다.
- 이번 주 제한 오픈은 **파트너스 쪽만** 엽니다. 구매자 가입·주문(무통장 포함)은 제외합니다.
- 첫 파트너스 계정은 마스터 관리자의 「파트너스 직접 추가」(최고관리자 전용)로 만듭니다. **현재 코드에는 이 경로가 없습니다**(`app/api/admin/sellers`에 목록·검토·내보내기·메모만 있고 생성 경로 없음, 시드는 `OBS_TEST_MODE=1`에서만). 기반-마스터 설계와 디자인 정본이 먼저입니다.

### 7.1 1단계 — 파트너스 쪽 제한 오픈(이번 주)

열리는 범위(결제·본인확인 공급자 호출 없음):
- 파트너스 로그인, 방송·오버레이·주문대기(OBS) 화면과 API
- 상품·진열·주문 관리 화면과 API
- 체험 기간(`trialEndsAt`) 안의 이용. 카드 등록이 필요해지는 시점부터는 아래 막힌 범위에 걸립니다.

막혀 있어야 하는 범위(현재 코드 동작, 오픈 중에도 그대로 둠):
- 구독 카드 등록·이용권 변경·충전금 충전·자동 연결 구매/재연결·구독 환불 승인·실패 청구 재시도: `billingProvider()`가 운영에서 오류(호출 경로 7곳).
- 파트너스 가입 신청(대표자 본인확인), 아이디 찾기(`/api/seller/find-id/*`), 직원 본인확인 연결: 503 「본인확인 서비스 준비 중이에요」.
- 국세청·공정위 자동 점검: 조회 실패로 처리되어 신청 사유에 남습니다.

1단계 시작 조건: 위 「파트너스 직접 추가」 경로 구현·병합, 체험 기간이 끝나기 전 구독 결제(3단계)가 준비되는지 일정 확인(체험이 끝나면 카드 등록이 필요해 잠깁니다).

### 7.2 2단계 — 본인확인 계약·키 뒤 구매자 가입
- 필요: 포트원 계약, `PORTONE_API_SECRET` · `PORTONE_STORE_ID` · `PORTONE_IDENTITY_CHANNEL_KEY`(어댑터는 구현돼 있음).
- 구매자 가입 `POST /api/shop/{slug}/signup`과 `/signup/verification`은 항상 본인확인을 거치며 공급자가 없으면 503입니다. 주문·견적 API는 구매자 세션이 없으면 401이라, 이 단계 전에는 구매자가 가입도 주문도 할 수 없습니다.
- 본인확인을 켤 때 함께 정할 보류 항목: SH-011-2(이미 가입한 사람 표시, `already_member` 409의 개인정보 노출 범위), 인증번호 만료 시각 표시. 둘 다 본인확인 가입 흐름 안이라 1단계 범위에서 빠집니다.

### 7.3 3단계 — 결제 계약·어댑터 뒤 카드 결제·구독 결제
- 구독 카드 자동결제: 업체 선정·계약과 어댑터 구현이 먼저(§3).
- 주문 카드 결제: 운영 계약 뒤 나이스페이 **운영 주소**를 부르는 코드 변경이 먼저(§3).
- 업체명이 정해지기 전에는 이 코드 작업을 서버 세션에 배정하지 않습니다(MASTER 결정).
- 무통장 주문은 카드와 별개 코드(`lib/server/payments/bank.ts`)이지만 구매자 가입이 필요해 2단계 이후입니다.

### 7.4 SH 보류 항목 구분

| 항목 | 공급자 의존 | 판단 |
| --- | --- | --- |
| SH-011-2 이미 가입한 사람 표시 | 본인확인 가입 흐름 안 | 1단계 범위 밖, 2단계에서 처리 |
| 인증번호 만료 시각 표시 | 본인확인 가입 흐름 안 | 위와 같음 |
| SH-003 서버 항목(LIVE·쿠폰·적립·재고·평점) | 공급자 호출 없음(표시 항목) | 1단계 범위 밖(구매자 화면), 오픈 차단 아님 |
| SH-005 결제 버튼(「주문하기」 유지) | 문구 확정, 공급자 무관 | 영향 없음 |

### 7.5 2단계 이후 무통장 흐름 실측 경로(시험 정비·화면 대조 SH 전달용)

구매자 가입이 본인확인을 요구하므로, 지금 실측은 **운영 빌드 + 테스트 모드(`NODE_ENV=production`, `OBS_TEST_MODE=1`, `NICEPAY_*` 비움)**의 로컬 빌드에서 합니다(본인확인 가짜 공급자, 인증번호 000000. 테스트 서버 환경변수는 바꾸지 않음).

1. 조건: 파트너스 쇼핑몰 `ACTIVE`, 판매자 입금 계좌 등록(`PUT /api/seller/payments/bank-account`, 화면 위치는 확인하지 못함), 판매 중 상품 1개 이상, 카드 키 없음.
2. 구매자: `/shop/{slug}/signup` → `/shop/{slug}/products/{productId}` → `/shop/{slug}/cart` → `/shop/{slug}/checkout`.
3. 확인: 카드 선택 시 「결제 준비 중」 거절(`POST /api/shop/{slug}/orders`), 무통장 선택 시 `POST /api/shop/{slug}/payments/bank-transfer`로 입금 안내, `/shop/{slug}/orders/{orderId}`에서 입금 기한·계좌 표시.
