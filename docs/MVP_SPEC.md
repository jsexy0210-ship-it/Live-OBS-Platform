# LifeLeft / 인생잔량 — MVP 기준서

> **상태:** MVP 개발 기준본  
> **서비스명:** 인생잔량 (LifeLeft)  
> **목표:** 짧은 입력 → 강한 숫자 결과 → 근거 확인 → 공유 → 관련 계산기로 이어지는 한국어 웹 서비스  
> **수익화:** 검색 유입 + 공유 유입 + 디스플레이 광고  
> **운영 원칙:** 1인 운영, 최소 백엔드, 최소 외부 의존성, 사용자 입력값 서버 미저장

---

## 1. 서비스 한 줄 정의

**출근도, 월급도, 주말도 무한하지 않습니다. 지금까지 얼마나 썼고 앞으로 얼마나 남았는지 계산합니다.**

메인 카피:

> **당신 인생, 얼마나 남았을까요?**

서브 카피:

> 출근도, 월급도, 주말도 무한하지 않습니다.

---

## 2. MVP 목표

초기 버전은 아래 5개 계산기만 제공한다.

1. 출근잔량
2. 주말잔량
3. 월급잔량
4. 구독료 계산기
5. 회사에 쓴 시간

MVP에서 중요한 것은 기능 수가 아니라 다음 흐름이다.

```text
질문
→ 최소 입력
→ 큰 숫자 결과
→ 계산 근거
→ 공유
→ 다른 계산기
```

사용자는 첫 결과까지 가급적 **20~30초 이내**에 도달해야 한다.

---

# 3. 핵심 UX 원칙

## 3.1 결과가 먼저다

결과 화면의 가장 중요한 숫자를 크게 노출한다.

예:

> 퇴직까지  
> **5,842번**  
> 더 출근해야 합니다.

또는:

> 구독 서비스에 지금까지  
> **4,283,400원**  
> 썼습니다.

숫자 아래에는 짧은 해석 문구를 붙인다.

예:

> 오늘도 1회 차감됐습니다.

---

## 3.2 입력은 짧게

각 계산기의 필수 입력은 최대한 3~4개 수준으로 유지한다.

정확한 값을 모르는 사용자를 위해 다음을 허용한다.

- 기본값
- 대략적인 기간 선택
- 선택 입력
- 나중에 수정

완벽한 입력을 요구해 결과까지 도달하지 못하게 만드는 UX를 금지한다.

---

## 3.3 결과 신뢰 등급

모든 결과는 아래 셋 중 하나로 명확히 분류한다.

### 정확 계산
사용자 입력값과 날짜 계산만으로 결정되는 결과.

예:
- 현재 월 구독료 합계
- 현재 날짜부터 지정 은퇴일까지 남은 급여 횟수

### 공식통계 기반
정부·공공기관의 공식 데이터와 사용자 입력을 함께 사용한 결과.

예:
- 공식 근로시간 통계와 사용자 근무시간 비교
- 국가 생명표를 활용한 통계적 참고치

### 예상 시뮬레이션
미래 가정을 포함한 결과.

예:
- 연봉 상승률을 적용한 총 예상 급여
- 물가상승률을 적용한 미래 생활비

**통계·시뮬레이션 결과를 개인의 미래 사실처럼 단정하지 않는다.**

# 4. 공통 결과 구조

모든 계산기의 결과 화면은 최대한 동일한 패턴을 사용한다.

```text
[결과 유형 Badge]

퇴직까지
5,842번
더 출근해야 합니다.

[짧은 해석]

[광고 슬롯]

[세부 결과]

[계산 근거 보기]

[공유하기]

[다른 잔량 확인하기]

[광고 슬롯]
```

## 계산 근거 영역

반드시 아래 항목을 제공한다.

- 사용한 입력값
- 계산식
- 적용한 가정
- 데이터 기준일
- 데이터 출처
- 마지막 데이터 갱신일

# 5. MVP 기능 상세

## 5.1 출근잔량

### 질문

> 퇴직까지 몇 번 더 출근해야 할까요?

### 입력

- 출생연도 또는 현재 나이
- 예상 은퇴 나이
- 주 근무일
- 연간 예상 연차 사용일

### 결과

- 남은 예상 출근 횟수
- 남은 월요일 수
- 남은 근무시간
- 남은 회사생활을 년/개월/일로 환산

### 계산 기준

기본적으로:

```text
오늘 ~ 예상 은퇴일 사이의 평일
- 대한민국 공식 공휴일
- 예상 연차 사용일
= 예상 남은 출근일
```

회사 자체 휴무일, 병가, 실제 휴직 등의 개인 조건은 기본 계산에서 제외하며 결과에 가정을 표시한다.

### 결과 유형

**공식 일정 기반 계산**

---

## 5.2 주말잔량

### 질문

> 앞으로 주말을 몇 번 더 보낼 수 있을까요?

### 입력

- 출생연도
- 계산 기준 나이

기본 기준 나이는 사용자가 선택한다.

예:
- 70세
- 80세
- 90세
- 직접 입력

### 결과

- 지금까지 보낸 주말 수
- 앞으로 남은 주말 수
- 앞으로 남은 여름 횟수
- 앞으로 남은 연말 횟수

### 원칙

기본 모드는 사용자가 선택한 기준 나이까지 단순 계산한다.

국가 생명표를 활용하는 별도 통계 모드를 추가하는 경우 반드시 아래 취지를 표시한다.

> 국가 생명표 기반 통계적 참고값이며 개인의 실제 수명을 예측하지 않습니다.

### 결과 유형

- 기본: **정확 계산**
- 통계 모드: **공식통계 기반**

---

## 5.3 월급잔량

### 질문

> 앞으로 월급을 몇 번 더 받을까요?

### 입력

- 현재 월 급여
- 세전 / 실수령 선택
- 급여일
- 예상 은퇴 나이
- 선택: 연봉 상승률

### 결과

- 앞으로 받을 예상 월급 횟수
- 현재 월급 유지 시 총액
- 연봉 상승률 적용 시 총 예상액
- 연간 / 5년 / 10년 금액

### 원칙

현재 월급이 그대로 유지된다고 가정한 결과와 연봉 상승률을 반영한 시뮬레이션을 분리한다.

### 결과 유형

- 횟수: **정확 계산**
- 미래 금액: **예상 시뮬레이션**

---

## 5.4 구독료 계산기

### 질문

> 지금까지 구독료로 얼마를 썼을까요?

### 기본 서비스

- Netflix
- YouTube Premium
- Disney+
- TVING
- Wavve
- Coupang WOW
- Melon
- Spotify
- Apple Music
- iCloud
- Google One
- ChatGPT
- Claude
- 기타

### 서비스별 입력

- 실제 월 결제액
- 이용 시작년월

선택:
- 중간에 사용하지 않은 기간

### 결과

- 지금까지 사용한 예상 총 구독료
- 현재 월 정기결제 총액
- 1년 예상 구독료
- 향후 5년 예상액
- 향후 10년 예상액
- 서비스별 지출 비중

### MVP 계산 원칙

초기에는 서비스의 과거 공식 요금 변동을 임의 추정하지 않는다.

**사용자가 입력한 실제 월 결제액을 최우선**으로 사용한다.

과거 요금제 이력 DB를 구축한 이후에는:

```text
서비스
- 요금제
- 적용 시작일
- 적용 종료일
- 가격
- 공식 출처
- 확인일
```

구조로 관리한다.

### 결과 유형

**사용자 입력 기반 계산**

### 결과 주의 문구

> 할인, 통신사 결합, 가족 공유, 중도 해지 기간 등은 입력하지 않은 경우 반영되지 않습니다.

## 5.5 회사에 쓴 시간

### 질문

> 지금까지 회사에 인생을 얼마나 썼을까요?

### 입력

- 직장생활 시작년월
- 하루 평균 근무시간
- 왕복 출퇴근시간
- 주 근무일

선택:
- 하루 평균 야근시간
- 주간 평균 회의시간

### 결과

- 지금까지 근무에 사용한 시간
- 출퇴근에 사용한 시간
- 선택 입력 시 야근/회의 시간
- 전체 합산 시간
- 년/개월/일 환산

### 비교 기능

공식 근로시간 통계 데이터가 준비되면:

- 사용자 월평균 근무시간
- 공식 통계 평균
- 평균 대비 차이

를 추가한다.

### 결과 유형

- 개인 시간: **사용자 입력 기반 계산**
- 평균 비교: **공식통계 기반**

# 6. 공공데이터 / OpenAPI 전략

사용자 계산 순간마다 외부 API를 직접 호출하지 않는다.

기본 구조:

```text
공공 API
↓
정기 수집 / 데이터 갱신
↓
내부 JSON 또는 정적 Snapshot
↓
계산 엔진
↓
사용자 결과
```

목적:

- 외부 API 장애 시에도 서비스 정상 동작
- 응답속도 안정화
- API 호출량 최소화
- 결과에 기준일 표시 가능
- 데이터 변경 이력 관리 가능

# 7. 데이터 라이선스 원칙

공공데이터라고 해서 무조건 광고 서비스에서 자유롭게 사용할 수 있다고 가정하지 않는다.

데이터 도입 전 확인:

- 상업적 이용 가능 여부
- 변경 허용 여부
- 출처 표시 조건
- API 이용약관
- 재배포 가능 여부

공공누리 제4유형 등 **상업적 이용금지 데이터는 광고 수익 서비스에 사용하지 않는다.**

모든 외부 데이터는 아래 메타정보를 관리한다.

```text
sourceName
sourceUrl
license
referenceDate
lastUpdatedAt
commercialUseAllowed
```

# 8. 개인정보 / 사용자 입력

## 기본 원칙

- 회원가입 없음
- 로그인 없음
- 개인 입력값 서버 저장 없음
- 이름 / 전화번호 / 이메일 수집 없음

사용자 입력 보존이 필요한 경우 브라우저 `localStorage` 사용.

화면 안내 예:

> 입력한 정보는 이 기기에만 저장되며 서버 계정정보로 저장하지 않습니다.

# 12. 광고 수익화 구조

MVP 개발 시 실제 광고 SDK 연결은 필수가 아니다.

재사용 가능한 `AdSlot`만 먼저 구현한다.

권장 위치:

1. 결과 Hero 아래
2. 계산 근거 / 세부 결과 아래
3. 관련 계산기 전후 중 필요 위치

광고가 아직 없어도 레이아웃이 무너지지 않아야 한다.

광고만 있고 콘텐츠가 빈약한 페이지를 만들지 않는다.

각 계산기 페이지에는:

- 계산 기능
- 계산 방식 설명
- 기준 데이터 설명
- 자주 묻는 질문
- 관련 계산기

등 자체 콘텐츠를 포함한다.

# 13. Analytics

MVP에서는 wrapper만 준비하고 실제 분석 SDK 연결은 이후 설정 가능하게 한다.

예상 이벤트:

- `calculator_view`
- `calculation_complete`
- `result_share`
- `related_calculator_click`

금지:

- 실제 월급
- 생년
- 보유자산
- 실제 구독금액
- 기타 민감한 입력값

을 이벤트 payload로 보내지 않는다.

# 15. 디자인 방향

참고 UX:

- 짧은 질문
- 최소 입력
- 결과 숫자 극대화
- 강한 한 줄
- 근거 확인 가능
- 즉시 공유

톤:

- 결과 카피는 직관적이고 약간 자극적
- 계산 근거는 보수적이고 정확하게
- 불필요한 전문용어 최소화

즉:

> **겉은 자극적으로, 계산 엔진은 보수적으로.**

# 17. MVP 이후 우선순위

MVP 배포 이후 기능을 한꺼번에 추가하지 않는다.

우선순위:

1. **내 돈 언제 끝남**
2. 내 집까지 몇 년 남음
3. 과거 구독 서비스 가격 이력 DB
4. 공식 통계 비교 강화
5. 물가를 반영한 현재 가치 / 미래 가치
6. 공유용 이미지 고도화

트래픽과 검색 유입 데이터를 보고 다음 기능을 결정한다.

# 18. 프로젝트 운영 원칙

- 최신 GitHub `main`을 Source of Truth로 사용한다.
- 문서와 코드가 충돌하면 최신 확정 정책을 먼저 문서에 반영한다.
- 기능 추가 전 기존 MVP 완료 여부를 먼저 확인한다.
- 범위를 불필요하게 키우지 않는다.
- 1인 운영 가능한 구조를 유지한다.
- 백엔드 도메인 ≤ 3
- 핵심 테이블 ≤ 5
- 사용자 여정 ≤ 5
- 외부 연동 ≤ 1을 기본 복잡도 기준으로 삼는다.

현재 MVP는 이보다 더 단순하게 **DB 0 / 회원 0 / 실시간 외부연동 0**을 목표로 한다.
